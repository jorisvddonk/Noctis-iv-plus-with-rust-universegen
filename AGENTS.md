# AGENTS.md

Rust port of the Noctis IV Plus universe generator, validated bit-for-bit
against the original Borland C++ 3.1 source compiled under DOSBox-X.

## Layout
- `source/NOCTIS-0.CPP`, `source/NOCTIS-1.CPP` — the **unmodified**
  reference C source (ground truth). Do not "fix" it; port bugs faithfully.
- `tests/nivgen/` — the Rust port (`rng.rs`, `system.rs`, `f80.rs`,
  `hash.rs`). `cargo test` runs RNG/f80/hash regression vectors.
- `tests/harness/NIVTEST.CPP` — the C harness that drives the reference
  source and emits the fixtures in `tests/results/*.OUT` (CRLF).
- `tests/scripts/run-niv-tests.sh --local` — rebuilds the C fixtures
  using native DOSBox-X (BCPP 3.1 from archive.org).
- `tests/db/` — SQLite database of canonical BCPP 3.1 FNV hashes for
  1004 stars, 319 planets with surface data, 647 bodies with sector data.
  Use `uv run python3 tests/db/query_db.py` to look up expected hashes.
- `tests/db/bulk_sectors.py` — **single entry point** for the full
  verification pipeline (sector gen + load + Rust compute + compare + surf).
  `one_iter` runs everything for the next star; `db-report` prints status.
- `tests/db/bulk_atlas.py` — bulk-import stars from Feltyrion Explorer
  (upstream of `bulk_sectors.py`, which only processes stars already in DB).
- `docs/src/porting-gotchas.md` — **read this before touching the RNG
  or float math.** Documents every non-obvious Borland behaviour discovered
  while porting, including the critical `imul ax` low-word replacement (§17).
- `docs/test-fixtures.md` — coordinates and body indices for every planet
  type across all star classes.
- `tests/rawsys3/` — **canonical ground-truth** OG-built module for raw
  system generation. Compiled with the original BC31 toolchain (no 2026
  harness code). **DO NOT MODIFY** `RAWSYS3.CPP` without extreme
  confirmation — before editing, call `ntfy` to escalate the decision.

  Usage:
  ```bash
  tests/rawsys3/build-and-run.sh X Y Z
  ```
  Takes user-facing Parsis coordinates (y negated on the galactic chart),
  normalises y sign internally via `-y`, and prints the star's class, body count,
  and per-body type/owner. Matches starmap/Feltyrion output exactly.

## Critical rules
1. Reproduce bugs, do not "correct" them. The Rust must match the C
   fixtures byte-for-byte (CRLF included).
2. For **system gen** (star class, body count, planet types), the canonical
   ground truth is `tests/rawsys3/build-and-run.sh` output — NOT the 2026
   `NIVTEST.EXE` system command. RAWSYS3 is built with the original BC31
   toolchain and has no 2026 modifications. The Rust `generate()` normalises
   the y sign via `EngineY::from_user_y()`. Passing a wrong-convention y
   is a compile-time type error (§30).
2. The most common divergence sources are **16-bit `int`/`unsigned`
   arithmetic**, **`imul ax` low-word replacement**, and **x87 80-bit
   float precision**. See the gotchas doc.
3. Never commit `tests/nivgen/target/` (already gitignored).
4. Always compare against BCPP 3.1 output (`run-niv-tests.sh --local`),
   not the old Turbo C++ 3.0 container build.

## Current status (2026-07-21)
**100% of surface maps match (838/838 bodies)** across 40 star systems
(235 planets + 511 moons). **588/589 palette hashes match** — the single
remaining `pal` mismatch is TWENDZ body 13 (type-7 planet data artifact, not
a port bug). Systems span all star classes S00-S11 (class-diverse corpus drawn
from the Feltyrion Explorer atlas via `tests/db/bulk_atlas.py`).

**Critical: canonical comparison MUST use `planet-all`, not single-body
`planet -p N`.** Canonical fixtures are generated by `recompute-canonical.sh`
via `NIVTEST.EXE planet-all`, which shares per-body state (the darkside
terminator for a moon of a non-type-10 owner depends on prior bodies' `plx/plz`).
`bulk_sectors.py one_iter` runs `nivgen planet-all` once per star for this
reason; comparing single-body output against the all-body fixture falsely diverges
(e.g. YU body 17). See §19/§24.

Surface hashes cover **only rows 0-127 (46080 bytes)** of the 360×180 map —
the region the globe renderer can actually sample (rows 0-121). The scratch
tail (rows 128-179) is never displayed and is nondeterministic for moons
(far-heap OOB read), so it is excluded from hashing. See §19.

Match rate by planet type (planet / moon):
- **100% both planet and moon**: all types (0-9)

### Fixed
- **Crater**: crays per-angle (not per-gr), second block per-angle, borrow
  check (JNC=CARRY, not sign), 16-bit `unsigned px, py` truncation
- **Wave** (type 6): the inline-asm `add ax, 4` before the `es:[di]` write
  provably has NO effect on the written offset — verified byte-for-byte
  against the C surfmap, `di` is `py*360 + px`, not `+ 4`. Dropping the
  spurious +4 took type-6 planets to 100%.
- **Fracture**: the globals `a`, `px`, `py` are Borland `float` (32-bit) —
  the angle and position accumulators re-round to f32 every iteration
  (cos/sin promote back to double); `kfract` is also `float`. Accumulating
  in f64 drifted over the 100-200 fracture calls per body. 16-bit py
  `(unsigned)` cast before *360. This fix took types 0, 4, 7 to 100%.
- **psmooth_grays**: packed 4-row dword average (was wrong 2×2 block)
- **surf_case3** (felisian): `add ax, cx` (loop counter), `imul ax` low-word
  replacement, `mov word ptr` zeroing
- **Terminator**: 16-bit `di` wrap in darkside
- **F80 add**: exponent alignment, carry check (`s>>63==1` → `!= 0`)
- **Shade**: Borland `k`/`delta_*`/`start_*` are `float` (32-bit), so each
  gradient step rounds back to f32. Accumulating in f64/F80 drifts the
  64-colour ramp and broke type-7 **planet** palettes. Pure per-step f32
   rounding took type-7 planets to 100% (see §23/§26). Type-7 moons
   also now match (see `docs/src/type7-palette-investigation.md`).
- **Moon surfaces**: the moon far-heap OOB read (lssmooth past `s_background`)
  lands in scratch rows the game never renders. Fix = hash only the sampled
  rows 0-127 (`SAMPLED_BYTES=46080`), which is fully deterministic across
  single-body / planet-all / in-game. Moons now match at their planet-type
  rate (see §19).
- **Type 5** (`contrast`/`randoface`): Borland evaluates function arguments
  **right-to-left**, so multiple RNG calls within one call statement consume
  values in reverse argument order. Fixing `contrast(...)` and
  `randoface(...)` took type-5 planets to 100% (28/28). See §20.
- **Type 3** (`atm_cyclon`): the `float a` angle accumulator is stepped by
  the `double deg`. Borland computes `a += 6*deg` in double then rounds to
  f32; the port pre-rounded the step (`(6.0*DEG) as f32`), drifting `a` by
  ~1 ULP and flipping a `cirrus` write at an integer boundary. Fixing the
  initializer and the step took type-3 moons to 100% (9/9). See §22.
- **Type 5** (`contrast`): all operands/dest are Borland `float`, so the
  chain rounds to f32 per step. The port had emulated it with 80-bit `F80`,
  which drifted 1 ULP and broke a type-5 moon. Pure f32 per step took type-5
  moons to 100% (24/24). See §23.
- **`planet_xyz` moonorigin**: for a moon, C's `planet_xyz` adds the owner's
  orbital offset via `moonorigin()` (NOCTIS-0.CPP:1459). The port omitted it,
  leaving the moon at the wrong world position. This only surfaces when the
  moon's owner is a **type-10 companion star**, because only then does
  `cplx_planet_viewpoint` call `planet_xyz(logical_id)` and feed the stale
  `plx/plz` into the darkside terminator (`plwp`). One type-6 moon
  (TRIVIAPOLEN) had its terminator band misplaced. Fixing it took the port
  to **100% (371/371)**. See §24.

### Known (sector — root cause confirmed not in round_hill loop)
- `round_hill` (NOCTIS-1.CPP:1494): The C loop uses `int x, z` with
  **unsigned**-mix loop bounds. `cx - r` (int − unsigned) converts cx to
  unsigned, subtracts, assigns to `int x` as a potentially negative value.
  However, the loop condition `x < cx + r` then compares `int` with
  `unsigned`, promoting `x` to unsigned — so a negative `x` becomes a huge
  unsigned (> `cx + r`) and the loop **never executes** when `cx < r`.
  The Rust correctly emulates this with `(cx as u32).wrapping_sub(r)` and
  an unsigned `x < x1` comparison. The `int` declaration is a red herring
  — the unsigned-mix comparison is what matters. See §31.
  Full investigation: `docs/src/sector-float-precision.md` (2026-07-22).

### Remaining sector differences (x87 vs IEEE float precision)
All sector heightmap/Objectschart mismatches (~19880/40000 pixel diffs of
±1) are caused by **x87 80-bit vs IEEE 754 64-bit cos/sqrt differences**
in `round_hill`. The key computation `cos(d/v) * h` occasionally differs
by 1 ULP in the f32 result, which truncates to a ±1 integer difference.

The `round_hill` function is used ONLY by the sector code (NOCTIS-1.CPP
`build_surface`), not by the surface map code (NOCTIS-0.CPP
`gen_planet_surface`). The surface code uses `kfract`/`crater`, which
were separately fixed for f32 per-step rounding. This explains why all
surface maps match (838/838) while sectors can drift by 1 per pixel.

Additionally, the `asterism` inner loop's `ang` accumulation may differ
by 1 iteration between x87 (f80 stack, no intermediate rounding) and
Rust (f32 rounded per iteration), shifting subsequent RNG values. This
was verified to match exactly — see `docs/src/asterism-investigation.md`.

Fix options:
1. Accept ±1 tolerance for sector height comparisons (pragmatic).
2. Use x87-compatible cos/sqrt (extern C or inline asm) — not portable.
3. Run sector generation via DOSBox-X only (defeats porting purpose).

The `asterism` inner loop's `ang` accumulation was verified to match C x87
exactly for all density values [6,30] — see `docs/src/asterism-investigation.md`.
The RNG sequence through `oc_addtrees` is identical between C and Rust.

Full investigation: `docs/src/sector-float-precision.md` (2026-07-22).
- **Jitter guard (2026-07-20).** C condition `if (!waswet || (waswet &&
  !random(5)))` runs the heightmap jitter only when `random(5)==0` (1 in 5
  chance for wet worlds). The port inverted the test (`random(5) != 0`),
  jittering 4 out of 5 times instead of 1. Fixed to `_r5 == 0`. Body 5
  (type 3) heightmap now byte-exact. See §27.
- **Objects `nr_of_objects` reset (2026-07-20).** C line 2624 resets
  `nr_of_objects = 0` on flat pixels when `if (waswet)` — referencing the
  global `waswet`, not a local. The port declared and tested a dead local
  `liquid_water` that was never set to 1. Fixed to `self.waswet != 0`. Body 5
  objectchart now byte-exact. See §28.
- **Type-8 quartz tail (2026-07-20).** C line 2393 adds a shared tail after
  the type-8 feature block (hills/craters/jitter): `if (!random(5)) quartz=1`.
  The port omitted it. Added `if self.rng.random(5) == 0 { self.quartz = 1; }`
  in the type-8 match arm. AWELER bodies 0 & 9 (type 8) now byte-exact.
- `recompute-sector.sh` now exists (mirror of `recompute-canonical.sh`,
  invokes the harness `sector` command per body/landing) and is verified to
  reproduce the committed canonical byte-for-byte. Use it to (re)generate
  canonical sector fixtures.
- **Landable-range bug fixed (2026-07-20):** the pseudo (`rand`) landing
  coords came from `lat = (s // 1000) % 121`, which can emit lat **0** or
  **120** — both OUTSIDE the in-game landable latitude bounds of **[1, 119]**
  enforced by `NOCTIS.CPP:951-955` (`landing_pt_lat > 119 → 119`,
  `< 1 → 1`). Longitude `% 360` → [0, 359] is fine (game wraps it). The old
  formula hit lat 0 (236 bodies) and lat 120 (119 bodies) corpus-wide; CHOALUUS
  happened to avoid both. `coords_from_seedval` now returns
  `lat = 1 + ((s // 1000) % 119)` (∈ [1, 119]), keeping fixtures on landable
  ground. Canonical `rand` fixtures must be regenerated with the clamped
  coords (the `def` landing at lat 60 is unaffected).

### Known non-surface gaps
- **Moon surface SECTOR divergence (5 bodies across 2 stars; bodies CHOALUUS
  27/61/75 and VOIDAL LAMP 24/28 — heightmap and/or objectchart, seedval
  pseudo landing only).** NOT the §19 far-heap gap: `build_surface`
  (NOCTIS-1.CPP:1974-1975) reseeds both `fast_srand` and `srand` from
  `global_surface_seed` at its start, so the RNG state from
  `gen_planet_surface` (where the tail lives) cannot affect the sector.
  All 5 bodies match on the default landing (lon=0, lat=60); divergences are
  triggered by specific seedval-derived landing coordinates through
  latitude-sensitive branches in `setup_landing` or `build_surface`.

  Binary diff of C vs Rust objectschart (body 24, type 2 moon) shows only
  6 differing bytes across all 40000:
  - bytes 150-151: C has c0=3(invalid)/c1=1(VEGET), Rust has c0=0(ROCKS)/
    c1=0(ROCKS). The OC_GAP theory was disproven (gap changes have no
    effect on output). The `addtrees` code path (lines 2240-2251) is the
    only code that writes VEGET/TREES, but C's case 2 has a `break` before
    the case-3 `switch(sctype)` that leads to `addtrees`. The C byte values
    don't match `addtrees` output (c2 should be VEGET but is ROCKS).
    Root cause of the object class discrepancy is still unclear from static
    code analysis — possible Borland C++ bitfield packing quirk or an
    undocumented code path. See `docs/src/porting-gotchas.md` §29.
  - bytes 39966-39973: `nr_of_objects` nibbles differ near the buffer end
    (downstream of the class placement issue).

  The same pattern extends to CHOALUUS 27/61 (hm matches, oc differs) and
  CHOALUUS 75 (both hm+oc differ). Under investigation.

## Canonical hashes (BCPP 3.1 / DOSBox-X only)
Canonical hashes MUST come from the real toolchain under DOSBox-X. Never
generate them any other way.
```bash
# Full pipeline for one star (gen + load + Rust compute + compare + surf):
uv run python3 tests/db/bulk_sectors.py one_iter <STAR_NAME>

# Or auto-select the next unprocessed star:
uv run python3 tests/db/bulk_sectors.py one_iter

# Print status report (always use this for reporting):
uv run python3 tests/db/bulk_sectors.py db-report

# Seed new stars from Feltyrion Explorer (upstream of bulk_sectors):
uv run python3 tests/db/bulk_atlas.py run --per-class 2
```
